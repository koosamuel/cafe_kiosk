## 3. 발견된 누락·불일치·개선점

P0는 제출 전 반드시 수정하거나 미구현으로 공개해야 할 문제, P1은 재현성과 설명을 위해 보강할 문제다. 이번 수정에서 새로 발생한 문제와 기존 한계를 구분했다.

### R1 [P0] 복합 주문의 옵션이 다른 음료에 전파됨 — 기존 결함

- 위치: `rag-assistant.js:329,514`, `app.js:924~930`.
- 입력: `아이스 아메리카노 레귤러 하나랑 따뜻한 카페라테 라지 하나 담아줘`.
- 실제: 두 품목 모두 `temp-ice,temp-hot,size-large,size-regular`를 받는다. `ragOptionsFor`는 그룹의 첫 옵션을 선택하므로 현재 배열 순서에서는 둘 다 HOT/Regular로 적용될 수 있다.
- 원인: 품목별 segment에 전체 text를 다시 합쳐 옵션을 추출한다. 품목별 옵션 범위와 그룹별 단일 선택을 강제하고, 앞에 나온 온도도 해당 메뉴 구절에 붙여야 한다. 후속 수정은 그룹값을 대체해야 한다.

### R2 [P0] 무카페인·무당·따뜻한 차의 AND 필터 미구현 — 기존 결함 + 신규 필터의 불완전성

- 위치: `rag-assistant.js:127~135,292~296,576~597`.
- 입력: `카페인 없고 당류도 없는 따뜻한 차 추천해줘`.
- 실제: 아메리카노와 얼그레이 추천. 둘 다 카페인이 있고 하나는 차도 아니다.
- 입력: `카페인 없는 음료 추천해줘` → 카페인 ‘매우 낮음’인 초콜릿 포함.
- 무카페인을 낮은 카페인과 혼합해 점수 가산할 뿐 하드 필터하지 않는다. 무당 필터는 현재 유자차를 제외하지만 `저당` 태그도 통과시켜 무당 의미를 약화한다. `당류 0g` 표현도 필터로 처리되지 않는다.
- 수치 필드·범주·온도를 모두 만족하는 후보만 반환하고 null은 안전 추천에서 제외해야 한다. 현재12개에는 G04의 캐모마일/민트가 없으므로 조건 만족0건을 안내하는 것이 맞다.

### R3 [P0] 부분 담기는 문구만 변경되고 실행은 안 됨 — 이번 수정의 미완성

- 위치: `rag-assistant.js:520~525`, `app.js:937~940`, `tests/rag-assistant.test.cjs:328~334`.
- completedActions를 계산하지만 반환 액션은 전체를 포함한 `pending_many`다. UI는 pending 상태만 저장하고 장바구니에 추가하지 않는다.
- 새 테스트는 ‘확인’·‘온도’라는 문자열만 검사한다. **즉시 담기·수량·중복 방지**를 검증하지 않는다.
- 실제 `menu.json:31~32`는 모든 푸드에 데우기 그룹을 적용하여 치즈케이크도 옵션 미완성이다. 테스트는 이 그룹을 빼고 만들어 실데이터와 다르다.
- 완성된 항목의 실행 결과와 미완성 항목의 pending 상태를 함께 반환·적용하고, 다음 턴에 이미 담은 항목이 중복되지 않도록 식별해야 한다. 치즈케이크 워밍 규칙도 수정해야 한다.

### R4 [P0] 영어 축약 주문과 영어 UI 계약이 깨짐 — 신규 영어 처리 불완전 + 기존 UI 문제

- 위치: `rag-assistant.js:70,236~237,340,527`, `app.js:85,1047~1052`.
- `I'd like a hot latte, medium, with oat milk` → `inform`, 액션 없음. normalize가 apostrophe를 공백으로 바꿔 `i d like`가 되지만 의도 정규식은 `i'd like`를 찾는다. `I'll have`도 같은 구조의 위험이 있다.
- `Can I get…`는 실제 menu.options 기준 HOT·Regular·Oat 모두 추출한다. 그러나 새 영어 테스트319~325행의 groupedOptions에는 오트가 없고, 오트 추출 assertion도 없다.
- 영어 UI는 옵션 그룹 `추가`를 `Extras`로 변환한다. 엔진은 문자열 `추가`만 선택 그룹으로 제외하므로 `Can I get a hot latte, medium?`에 Extras를 필수로 요구한다.
- 영어 UI의 `englishAssistantAnswer`가 엔진의 구체적 답변·적용 결과를 일반 문구로 다시 덮어쓴다. 번역 문자열을 도메인 판단에 쓰지 말고 group ID를 고정해야 한다.

### R5 [P0] 후속 답과 명시적인 메뉴 변경이 pending에 잘못 흡수됨 — 기존 결함

- 위치: `rag-assistant.js:62,214,419~503`.
- `아메리카노 담아줘 → 아이스 → M이요` → 크기 슬롯이 계속 비어 있음. `M이요`는 경계 정규식에 맞지 않는다.
- 아메리카노 pending 중 `그냥 유자차 핫 라지 주세요` → **유자차 대신 아메리카노**를 담는 액션.
- pending 단일/다중 분기가 새 메뉴 의도보다 먼저 실행된다. 다중 pending의 옵션 답변도 모든 메뉴에 일괄 전파한다.
- `pending_question`의 대상·슬롯·허용 답, 새로운 명시 메뉴의 우선순위, 취소/화제 전환/중간 질문 복귀 정책을 구현해야 한다.

### R6 [P0] 부분 취소 수량과 기존 항목 수정 미지원 — 기존 결함

- 위치: `rag-assistant.js:187~195,334~343,468~475`, `app.js:966~1005`.
- `아아 두 잔 중 한 잔 취소해줘. 총 얼마야?` → remove quantity **2**, 목표는1.
- `방금 그거 L로 바꾸고 샷 추가해줘` → 담을 메뉴를 다시 질문. 기존 cart line의 update/set_qty를 표현·적용하는 계약 자체가 없다.
- `parseQuantity`의 첫 수량을 모든 상황에 쓰지 말고 취소 대상 수량을 분리해야 한다. line ID 기반 수정, 대상 모호성 처리, 적용 후 최신 합계가 필요하다.

### R7 [P1] 진하기 비교가 정량 근거 없이 더 강하다고 단정 — 이번 수정에서 악화

- 위치: `rag-assistant.js:8~20,556~565`, `tests/rag-assistant.test.cjs:312~317`.
- 현재는 ‘카페인 높음/중간’만 있고 mg·샷수·사이즈 기준이 없다. 높음인 항목, 아니면 먼저 언급된 항목을 stronger로 고른다.
- 원본 지희94,161행은 맛과 카페인을 구분한다. 이번 코드는 ‘커피 풍미와 카페인이 더 강하다’로 다시 단정한다.
- 새 테스트도 ‘진한 풍미’라는 문구만 확인한다. 같은 카페인·미확인 값·다른 사이즈 비교를 검증해야 한다. 필드가 없으면 수치를 만들지 말고 비교 한계를 설명해야 한다.

### R8 [P1] 데이터·가격·메뉴 ID·정규화 규칙이 하나의 기준으로 연결되지 않음

- 위치: `HTI_통합본.md:4,36,40~51,87,169~180`, `menu.json:10~32`.
- 통합 시나리오의 Tall 아메리카노4,700원, 샷 비교150/75mg, 카푸치노·민트는 현재 실행 메뉴에 없다. 실제 Regular 아메리카노3,500원, 샷+500, 오트+700이다. 원본 가상 코퍼스의 샷+800·오트+600과 다르다.

- 엔진은 Tall→Regular, Grande/Venti→Large, Short→Small 또는 Regular로 압축한다. 이를 서로 다른 체계 간 별칭 매핑이라고 공개하고 지원하지 않는 용량은 별도로 안내해야 한다.
- N-1~N-9/D3를 인용하지만 통합본에는 해당 규칙의 본문·정의·참조 절이 없다. 원본 정의를 복원하거나 정확한 경로/절을 연결해야 한다.
- ‘공식 판매량 순위’ 등은 원본의 출처·기간·가상 점포 설정 여부를 보존해야 한다.

### R9 [P1] 대표 주문·추천 기능의 범위 및 테스트가 과장됨

- 위치: `HTI_통합본.md:16~19,164,187~192`; `rag-assistant.js:174~180,389~395,458~461,587~617`.
- 트리는31개인데37개라고 기록한다. 18/7/7/5의 기존 매핑을 새 Task ID와 다시 대조해야 한다.
- ‘커피 종류 전부 알려줘’ → 4개 중3개만 표시. 일반검색4개, 추천최종3개 제한이 있고 전체/카테고리/조건 목록 분기는 제한적이다.
- 가격을 사이즈 미지정으로 물으면 전체 사이즈가 아니라 기본 가격만 준다. 추천 본문에는 가격이 없다.
- `결제할게요`는 checkout 모달을 열 뿐, 대화의 `네`를 확정으로 연결하는 상태가 없다. 터치 확인 방식으로 시나리오를 바꾸거나 대화 확정을 구현해야 한다.
- 별칭 ‘아바라’는 메뉴는 찾지만 ICE를 채우지 않으며, ‘자허블’은 현재12개 메뉴/별칭 사전에 없다. 미판매 메뉴는 주문 미지원과 별칭 정규화를 구분해 설명해야 한다.
- `cartSummary`는 전달된 unitPrice를 계산한다. 보안 경계는 엔진이 아니라 주문 생성 RPC다. ‘모든 턴에서 서버 재계산’과 ‘최종 주문 서버 재검증’을 구분해야 한다.
- 무당 테스트305~309행의 `items`에는 유자차가 없다. 따라서 ‘유자차가 제외됨’ assertion은 오추천 방지를 검증하지 못한다. 실제 menu.items를 사용하고 결과 전체의 당류 조건과0건 처리를 검사해야 한다. 별도 재현에서는 현재 단순 무당 추천의 유자차 제외가 확인됐다.

### R10 [P1] 발표 요구사항과 현재 RAG 구현 설명이 불일치

- 위치: `HTI_통합본.md:131~158,162~192`, `03_구현계획.md:121~125`.
- 현재 sendRagMessage는 브라우저의 동기 함수다. 임베딩·벡터 검색·LLM·서버 세션을 연결한 구조도는 **목표 구조**로 구분해야 한다.
- 지희 원본154행은20분(8+5+5+2), PDF8쪽은 **발표15분+Q&A5분**이라고 기록한다. 실제 공지 원문은 확인하지 않았으므로 일정 확정은 불가하나, 두 자료의 충돌을 그대로 두면 안 된다.

## 4. 최종 발표·제출 및 main 병합 권장 액션

### 4.1 제출 전 우선순위

1. **완료 표현 수정**: ‘최종 확정’, ‘100% 포괄’, ‘29개 전수 해결’ 체크를 검증된 상태로 바꾼다. 각 요구를 `설계/구현/로컬검증/통합검증/미구현`으로 표시하고 증빙을 붙인다.
2. **P0 주문 정확성 수정**: 품목별 옵션 범위, 그룹값 대체, pending 새 메뉴 전환, M이요, 부분 취소, 완료 항목 즉시 담기 및 다음 턴 중복 방지를 우선 처리한다.
3. **건강 필터 수정**: 무카페인/디카페인/저카페인, 무당/저당/덜 단 맛을 분리한다. 미확인 수치와 조건 충돌은 안전한0건 안내로 처리한다.
4. **영어 통합 검증**: I'd like/I'll have/Can I get, 실제 오트 옵션, 영문 UI의 선택 그룹, 한국어↔영어 전환 중 pending 유지까지 검증한다.
5. **명세 복원**: 31개 또는37개 중 하나로 과업을 확정하고 원본 ID·합격 기준·근거 문서·코드·테스트 대응표를 작성한다. JSON 계약·13탭/현행5탭 선택·3열·더블클릭·접근성·복구를 추가한다.
6. **데이터 기준 고정**:12/162/316의 목적·출처·날짜·가격 검증 수준·주문 가능 여부를 표로 명시한다. 실행용 시나리오 가격/옵션은 실제 menu.json에 맞춘다.
7. **회귀 검증 보강**: 새 테스트의 문자열 검사를 상태·액션·옵션·수량·합계 검사로 바꾼다. 원본41건은 같은 입력·사전조건으로 재실행하여 전후표와 실패 로그를 저장한다.

### 4.3 Git 및 병합 평가

- 현재 체크아웃은 `feature/hti-feedback`이다. **로컬 HEAD/main/저장된 origin/main은 모두 `c949b7ed737c8cbba49c48f329b9392a626952ae`**이며 `git log main..HEAD`는 비어 있다.
- 기존 코드 변경은 `rag-assistant.js`135줄 추가/49줄 삭제, 테스트49줄 추가의 **미커밋 작업본**이다. `HTI_통합본.md`와 원본 자료도 untracked다. 브랜치 이름은 맞지만 변경이 브랜치 커밋으로 보존됐다고 말할 수 없다.
- 현 상태에서 PR/브랜치 merge만 수행하면 요청한 작업본 내용이 포함되지 않는다. 다른 브랜치로 전환할 때 이 변경이 따라갈 수도 있으므로 ‘브랜치로 안전하게 격리 완료’라는 설명은 수정해야 한다.
- 현재 로컬 기준 커밋 차이가 없어 텍스트 병합 충돌은 재현되지 않는다. 원격 fetch 없이 실제 최신 main과의 충돌 여부까지 확정할 수는 없다. 커밋 후 최신 main에 대해 격리된 작업 디렉터리에서 병합 검증이 필요하다.
- 동작상 위험은 크다. 엔진과 `app.js`의 pending/batch 계약, 영문 옵션 그룹, 실제 menu.options의 푸드 워밍, 문자열 중심 테스트 사이의 충돌은 텍스트 충돌 없이도 발생한다. `add_completed + pending` 같은 계약을 추가하면 엔진·UI·테스트를 함께 바꿔야 한다.
- 정적 배포는 `scripts/build-static.sh`가 명시한 파일만 복사한다. 162개 코퍼스를 폴더에 추가했다고 앱에 포함되거나 연결되는 것이 아니다. Git 저장/프로그램 제출과 정적 웹 배포 목록을 구분한다.
- 현재 서비스워커는 network-first(`sw.js:41~55`)이므로 캐시가 항상 최신 코드를 막는다고 단정할 수 없다. 다만 오프라인 이전 버전 혼합을 피하도록 자산 버전·캐시 이름을 함께 갱신하고 재접속/오프라인 시나리오를 검사한다.
- 권장 순서: 필요한 파일만 선별해 커밋 → 최신 main 차이 확인 → 위 P0 및 계약 통합검증 → PR에 실제 해결/미해결·실행 로그 명시 → 검토 후 병합. 이 검토에서는 커밋·push·PR·merge·배포를 실행하지 않았다.
